# Extension Iframe Content Not Independently Sanitized

## Summary

When the WASM module indicates that rendered content needs script execution (`parts.needs_iframe` or `parts.js` non-empty), the content script renders widget content into an iframe via `createIframeMount()`. The iframe content (generated by the WASM module) is NOT independently sanitized by the content script — it bypasses `sanitizeHTML()`. The iframe has `sandbox="allow-scripts"` (without `allow-same-origin`), so scripts can execute but cannot access the extension's origin. However, this design creates a risk surface where script execution and message-passing from the iframe are not fully constrained.

## Location

`crates/crepuscularity-webext/assets/content.js:342-345`:

```javascript
if (parts.needs_iframe || (typeof parts.js === "string" && parts.js.length > 0)) {
    return createIframeMount(() =>
        wasmModule.render_anywhere_frame_doc({ widget, unocss: unocssSource })
    );
}
```

`createIframeMount` at lines 259-283:
```javascript

    const srcdoc = frameSrcdoc(frameDoc);
    // ...
```

## Attacker Control

The attacker controls the `<pre>` element content on a third-party page. This content flows to the WASM module which generates the iframe document. While the WASM module is bundled with the extension, its output is influenced by the page content.

## Trust Boundary Crossed

Web page → Extension iframe (TB-5). Page content indirectly controls the iframe document content.

## Impact

**MEDIUM** — The iframe can execute arbitrary JavaScript via `sandbox="allow-scripts"`. While the sandbox prevents `allow-same-origin` (so scripts cannot access the parent page's DOM or cookies), the following risks exist:

1. **Message channel abuse**: `attachFrameResize()` listens for `message` events from the iframe — the iframe can send spoofed resize messages
2. **Resource exfiltration**: Iframes can make network requests and exfiltrate data via the browser's network stack
3. **Sandbox escape**: Browser sandbox bugs could allow the iframe to escape the sandbox and access extension APIs
4. **Social engineering**: Iframes can display phishing content styled to match the parent page

## Evidence

The iframe path bypasses `sanitizeHTML()` entirely. Compare:

**Inline path** (sanitized):
```javascript
const root = document.createElement("div");
root.innerHTML = sanitizeHTML(html);  // sanitized
```

**Iframe path** (NOT sanitized):
```javascript
const srcdoc = frameSrcdoc(frameDoc);  // frameDoc from WASM, not sanitized
frame.sandbox = "allow-scripts";
setIframeDocument(frame, srcdoc);
```

No call to `sanitizeHTML()` exists in the iframe path.

The `frameSrcdoc()` function at lines 149-162 constructs the iframe document:
```javascript
function frameSrcdoc(frameDoc) {
    if (!frameDoc) { return null; }
    return `<html><head><meta charset="utf-8"></head><body>${frameDoc.body || ""}</body></html>`;
}
```

The `frameDoc.body` comes directly from the WASM module's `render_anywhere_frame_doc()` output.

## Existing Mitigations

- `sandbox="allow-scripts"` without `allow-same-origin` (scripts can execute but cannot access parent page origin)
- Blob URL for iframe content (separate origin from parent page)
- Content runs in an isolated world (extension content script context)

## Reproduction Steps

1. Create a test page with a `<pre>` element containing content that causes the WASM module to set `needs_iframe: true`
2. Observe that the iframe is created with `sandbox="allow-scripts"`
3. The iframe document content is the raw output from WASM without content-script sanitization
4. Any JavaScript in the iframe executes (limited by sandbox)
